# M12 — Real JEV Choice Quality

## Research question

M11 measured choice quality for Random, the offline HeuristicJEV surrogate, and Oracle. M12 asks:

> Does the real JEV System-1 selector make good Destroy choices on the same local landscapes?

This is deliberately a **choice-quality** experiment, not another end-to-end benchmark.

## Protocol

M12 keeps the M11 protocol fixed:

- seeds: `1 2 3 4 5` by default;
- 50 iterations per seed by default;
- Random Repair;
- locally generated legal Destroy candidates;
- real JEV selects exactly one candidate ID;
- the local Oracle scores every available Destroy candidate after the decision;
- Oracle scores are diagnostic only and are never passed to JEV;
- the solver and acceptance rule are unchanged.

The intended comparison is:

| Selector | Purpose |
|---|---|
| Random | baseline |
| HeuristicJEV | offline surrogate control from M11 |
| Real JEV | M12 treatment |
| Oracle | local-choice upper control |

M11 controls are already available from the CI artifact; M12 does not require live JEV in CI.

## Run

Configure one of:

```text
JEV_API_KEY
TYPESAFE_API_KEY
OPENROUTER_API_KEY
```

For the OpenRouter setup used by this repository:

```dotenv
OPENROUTER_API_KEY=...
TYPESAFE_BASE_URL=https://openrouter.ai/api
JEV_MODEL=typesafe/jev-1.13
```

Then run:

```bash
python experiments/run_real_jev_choice_quality.py \
  --seeds 1 2 3 4 5 \
  --iterations 50 \
  --output experiments/runs/m12-real-jev-choice-quality
```

Outputs:

- `experiments/runs/m12-real-jev-choice-quality.json`
- `experiments/runs/m12-real-jev-choice-quality.md`

## Metrics

For each Destroy decision:

- **Top-1 rate** — selected candidate has the best downstream Oracle score;
- **Mean rank** — 1 is best;
- **Mean regret** — selected score minus the best score;
- **Normalized regret** — regret divided by the local score range.

M12 also records:

- JEV calls and successful calls;
- failures;
- fallbacks;
- low-confidence decisions;
- invalid choices;
- latency;
- input/output tokens;
- API cost.

## Fallback rule

A failed, invalid, or below-threshold JEV decision is handled by the existing deterministic fallback. Such a decision remains visible in the experiment, but the fallback count is reported separately.

Therefore M12 must not claim that all selected candidates were selected by JEV. When fallback rate is material, report both:

1. observed selector quality;
2. JEV acceptance/fallback rate.

## Methodological boundary

JEV sees the current serialized state, candidate IDs, state-aware candidate context, and the task objective. For Destroy decisions, each candidate context identifies the affected stacks, their destinations and heights, the top containers, and the containers exposed after destruction.

The candidate context is derived from the current state before the JEV call. It contains no downstream score, ranking, regret, or future outcome.

JEV never receives:

- Oracle downstream scores;
- candidate rankings;
- regret;
- future evaluation results.

The Oracle is evaluated after candidate selection and exists only as an offline measurement instrument.

## Interpretation

A strong M12 result would mean that real JEV chooses candidates with lower local regret than Random and the offline surrogate.

That still does **not** prove that JEV improves final VLNS solutions. The next question after M12 is whether improved local choice quality translates into better end-to-end search outcomes under the same repair and acceptance protocol.

A weak M12 result is also useful: it tells us that the bottleneck is already visible at the selector boundary, before adding more VLNS complexity.
