# M17 — Real VLNS Neighborhoods

## Research question

Does JEV select useful destroy neighborhoods when the search has a genuinely
variable neighborhood family rather than only single-stack and adjacent-pair
destroy operators?

M17 changes the candidate space, not the JEV decision boundary.

## Neighborhood model

For the current Container Stack state, a Destroy candidate is a combination
of non-empty stack indices.

The generator supports:

- min_stacks: smallest neighborhood size;
- max_stacks: largest neighborhood size;
- include_non_adjacent: whether arbitrary combinations are allowed.

With min_stacks=1 and max_stacks=3, the candidate family contains all
legal combinations of one, two, or three stacks.

Candidate order is deterministic.

For n non-empty stacks and K <= n, the number of candidates is the sum of
C(n, k) for k=min_stacks..K.

This is intentionally explicit: increasing K increases search breadth and
can increase the JEV choice space substantially.

## Why this is VLNS

The neighborhood size is no longer fixed to one operator shape. A run can
evaluate multiple neighborhood sizes and the selector chooses one candidate
from the complete generated family.

The implementation does not make JEV responsible for deciding:

- which stacks are legal;
- whether a stack is empty;
- how a candidate mutates state;
- how repair works;
- how the objective is evaluated.

Those remain deterministic environment/search responsibilities.

## Non-adjacent neighborhoods

Adjacent-only neighborhoods are insufficient to demonstrate a meaningful
large-neighborhood search family. M17 therefore supports arbitrary
non-adjacent stack combinations.

Adjacent-only generation remains available as a control via
include_non_adjacent=False.

## Physical objective boundary

M17 does not claim that a Destroy/Repair trajectory is a physical execution
plan.

Destroy and Repair remain virtual search transformations. The M16
ExecutablePlan boundary remains unchanged.

Therefore M17 results continue to use the existing projected search objective
unless and until the physical reconfiguration path is implemented.

## Controlled comparison

The first useful offline comparison should keep fixed:

- initial state;
- seed;
- iteration budget;
- Repair selector;
- acceptance rule;
- objective;
- candidate-generation policy.

The controlled variable is neighborhood family:

- K=1;
- K=2;
- K=3;
- optionally adjacent-only versus non-adjacent.

Real JEV should only be evaluated after the offline candidate-space tests are
stable.

## JEV boundary

JEV receives the generated legal candidates and state-aware candidate
contexts. It still returns exactly one candidate ID.

JEV is not given:

- Oracle scores;
- future evaluations;
- candidate rankings;
- regret;
- post-repair outcomes.

All JEV-facing runtime text remains English.

## Definition of Done

M17 is complete when:

- variable neighborhood sizes are configurable;
- non-adjacent neighborhoods are supported;
- candidate generation is deterministic;
- candidate legality remains outside JEV;
- larger destroys preserve the no-physical-cost search semantics;
- tests cover size, determinism, adjacency mode, and validation;
- offline comparisons can isolate neighborhood-family effects.
