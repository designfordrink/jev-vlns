# M10 — Visualization / Replay

## Status

M10 adds a research replay layer without changing the VLNS decision protocol.

The artifact is a step-by-step trace:

~~~text
state before iteration
  ↓
all legal Destroy candidates + Oracle downstream scores
  ↓
selected Destroy
  ↓
removed containers
  ↓
Repair candidates + selected repair
  ↓
projected objective
  ↓
accept / reject
~~~

## Generate a replay

~~~bash
python experiments/run_replay.py \
  --mode random-random \
  --seed 42 \
  --iterations 25 \
  --output experiments/runs/replay
~~~

This creates a machine-readable JSON replay and a self-contained HTML visualization.

Supported offline modes: `random-random`, `heuristic-random`, `oracle-random`.

## What the replay is for

M10 should answer:

1. Which candidates were available?
2. Which Destroy candidate was selected?
3. What was the best downstream Destroy score available?
4. What was the resulting Destroy regret?
5. Which containers were removed?
6. Which Repair choices were made?
7. Was the repaired solution accepted?
8. How did the projected objective change?

The Oracle landscape is diagnostic evidence only; it is not passed to the selector.

## Methodological rule

Replay is observational. With `capture_trace=False` the existing solver path remains unchanged. Tests verify that enabling trace capture does not change the final state, evaluation, or projected objective.

M10 does not establish JEV superiority. It provides evidence for understanding M9/M8 decisions before changing the solver.
